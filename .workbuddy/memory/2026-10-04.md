## v2.76（第七十二轮）：历史入口"钉不住"真因 —— 不是样式，是层级

### 起因

产品负责人第四次追问：「历史入口是否紧贴「Uni」下沿，且滚动时仍钉住。**还是有问题啊，怎么就修不好吗？这么简单的一件事**」

前四轮（v2.72~v2.75）我都在调**外观**：底色、毛玻璃、边框、负边距、去卡片化。每次改完"看起来好了"，真机一滚动又露馅。**方法错了。**

### 这轮改了方法：先量后改

装 `playwright`（+ `npx playwright install chromium`），起 dev server，登录演示账号 → 选北化 → 切 Uni 页，
用 `getBoundingClientRect()` 量两个元素的真实位置，**注入 1600px 高内容后滚 `<html>`**，再量一次。

铁证：

| 时刻 | `.head.top / .bottom` | `.uni-chat-history.top` | 缝隙 |
| --- | --- | --- | --- |
| 未滚动 | 0 / 66 | 66 | 0 px |
| **滚 500px（改前）** | 0 / 66 | **-434** | **-500 px** |
| **滚 500px（改后）** | 0 / 66 | **66** | **0 px** |

`-434` 说明：**它从来没真的 sticky 过**。未滚动时"看着贴住了"只是自然位置恰好在那儿。

### 真因（两条 CSS 规范约束叠加）

1. **祖先只要有 `overflow`（非 visible）就构成"约束容器"**。`.uni-chat-page` 带全局 `.scroll` 的
   `overflow-y: auto` → sticky 子元素只能在这个容器的高度范围内吸附，容器滚出视口它跟着走。
2. **真正在滚的是 `<html>`**。实测：`.screen` 是 `min-height: 100%` 而非 `height: 100%`，
   `.scroll { flex: 1 }` 拿不到确定高度 → `.uni-chat-page` 自己**永不滚动**
   （`clientHeight === scrollHeight === 2080`），只被内容撑开，交给页面级滚动兜底。
   `.head` 一直好使，正因为它**不在** `.uni-chat-page` 里。

### 修法（改层级，不是改样式）

| # | 改动 |
| --- | --- |
| 1 | 历史入口**移出** `.uni-chat-page`，与 `.head` 做兄弟 |
| 2 | 外包一层 `.uni-chat-wrap` 当根节点（SFC 只能一个根），`overflow: visible` 不裁剪 |
| 3 | `top: 0` → `top: var(--unih-head, 0px)` |
| 4 | 新增 `syncHeadHeight()`：挂载时量 `.head` 高度写 `--unih-head`；`resize`/`orientationchange` 重测；卸载 `removeEventListener` |
| 5 | 纵向负边距 `-12px` → `0`；横向 `-16px` 保留 |
| 6 | `.uni-chat-wrap` 补 `--unih-head: 0px` 静态兜底（`test:css` 的变量扫描器不认 `var()` 的兜底参数） |

模板里多包一层后，`.uni-chat-page` 的闭合位置要跟着调（在 `</section>` 后各加一个 `</div>`）。

### 教训（写给未来的自己）

## 桌面一键上传 bat（`D:\Desktop\上传到GitHub.bat`）

### 桌面路径

不在 `C:\Users\Gary\Desktop`，而是**重定向到 `D:\Desktop`**（`[Environment]::GetFolderPath('Desktop')` 在本环境回传空值，
`reg.exe` 被安全策略黑名单拦死 —— 最终靠**全盘搜 `desktop.ini`** 定位：`/d/Desktop/desktop.ini`）。

### bat 中文编码（**最关键的坑**）

| 编码 | chcp | 结果 |
| --- | --- | --- |
| UTF-8 无 BOM | 65001 | **坏**：REM 注释里的中文被 cmd 按 cp936 误读、**从中断裂**，碎片被当命令执行（报 `'接回车用默认的）。' is not recognized`） |
| **GBK (cp936)** | **936** | **好**：全部中文正确显示、零解析错误 |

**机理**：cmd 解析 bat 文件用的是**系统 ANSI/OEM 代码页**（中文 Windows = 936），**不是** `chcp` 设的那个。
`chcp 65001` 只改控制台**输出**代码页，所以 UTF-8 文件的中文能"显示对"，但**解析时**仍按 936 拆字节 → 多字节序列错位 → 行被撕裂。
**结论：中文 Windows 上的 bat 一律存 GBK + `chcp 936`。**（`.ps1` 相反，要 UTF-8 带 BOM；`.ts/.vue` UTF-8 不带 BOM —— 三种文件三种规矩。）

### 验证方法（可复用）

别再靠肉眼猜编码。**跑一遍 bat 把 stdout 重定向成二进制文件，再用 Python 试 `utf-8`/`gbk` 解码 + 查 `not recognized`**：

```bash
cmd //c "上传到GitHub.bat < nul > raw_out.bin 2>&1"
python -c "d=open('raw_out.bin','rb').read(); print(d.decode('gbk'))"
```
`< nul` 解决 `pause` 阻塞。**判据**：解码干净 **且** 输出里没有 `not recognized` 才算过。
注意 git bash 里 `iconv`/管道可能二次转码，直接 dump 字节最可靠。

`set /p` 输入提交说明（空则用默认 `更新 Unimate 项目`）；`git status --porcelain | findstr` 判断有无改动；
