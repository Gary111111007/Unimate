## 2026-09-26 真实请求结果（优化前历史基线）

最终默认模式为 `hybrid`：基础 Tool 意图由服务器规则产生结构化调用，普通聊天由蒸馏模型生成。

| 用例 | 结果 | 完整耗时 |
| --- | --- | ---: |
| 一句中文自我介绍 | `message`：`我是 Uni，一个面向大学生的聊天助手。` | 6,075 ms |
| 三轮上下文：追问刚才所说专业 | 正确记住“自动化专业” | 8,751 ms |
| 明天有什么课 | `getSchedule({"query":"tomorrow"})` | 1 ms |
| 记一下周五交高数作业 | `addNote({"title":"周五交高数作业"})` | 1 ms |
| 打开记事本 | `openFeature({"feature":"notes"})` | 1 ms |
| 把刚才的英语作业记到记事本 | 从上下文生成 `addNote` | 1 ms |
| 不提供 Tool 白名单，再问明天课程 | 只返回 `message`，没有越权 Tool Call | 2,889 ms |

## 纯 LLM Tool 模式的失败证据

设置 `PROTOTYPE_TOOL_MODE=llm` 后，虽然使用了 JSON Schema 约束和温度 0，仍观察到：

- 把“明天”错误映射成 `today`；
- 把“添加记事”错误选择为 `openFeature`；
- 把 `arguments` 输出为字符串，而不是 JSON 对象；
- 生成未授权 Tool 名或错误枚举；
- 将 Tool JSON 包进普通聊天文本。

网关白名单和参数校验正确拒绝了越权或畸形调用，但 1.5B 的语义准确率不足以直接执行真实 Tool。这里不通过放宽校验来掩盖模型问题。

## 2026-09-27 快速路径复验

现有 Windows x64 CPU 运行包执行 `--list-devices` 返回 `(none)`，不具备可用 GPU 后端。`--reasoning off --reasoning-budget 0` 对本模型没有产生有效提速；把普通聊天 token 降回 320 会出现正文为空，因此普通模型回答继续保留 512-token 预算。

本轮将高频、可确定处理的输入移到 `hybrid` 本地路由，真实 8787 HTTP 请求结果如下：

| 用例 | 结果 | 完整耗时 |
| --- | --- | ---: |
| 你好 | 本地 `message`，不调用模型 | 36.4 ms |
| 周五交高数作业 | 询问是否加入记事本，不调用模型 | 3.6 ms |
| 回复“是” | `addNote({"title":"周五交高数作业"})` | 5.5 ms |
| 帮我记一下周五交高数作业 | 先询问，不直接生成写入 Tool | 5.5 ms |

自动化测试还覆盖了回复“不用”时返回取消消息、数据 Tool 不执行，以及四条快速路径的上游模型调用次数严格为 0。

## 已验证 / 未验证

已验证：模型和运行包完整性、本机 CPU 加载、真实中文聊天、短上下文、混合模式结构化 Tool 结果、本地快速回答、待办询问/确认/取消、Tool 白名单安全边界、CORS 和内存限频的网关基础行为。

补充验证：临时浏览器聊天页在 `127.0.0.1` 与电脑局域网 IPv4 上均返回 200，同源 POST 能获得正确结构化 Tool Call。Cloudflare Quick Tunnel 官方接口连续两次超时，未获得公网 URL。

未验证：Android 真机接入、手机对局域网页面的实际访问、公网 HTTPS 隧道、并发与长时间稳定性、语音 ASR/TTS、真实数据库 Tool 执行、提醒通知、正式服务器成本与延迟。
