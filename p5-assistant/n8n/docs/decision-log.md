## D1 不用"巨型 AI Agent"做编排

| 项 | 内容 |
| --- | --- |
| **状态** | **采纳**（主规划 §三 D1） |
| **决定** | n8n 里**不存在**一个挂满全部 Tool、由模型自由决定调用的 Agent 节点。主链路确定性：标准化 → 规则识别 → 缓存 → 必要时 LLM 只做结构化解析 → `Switch` → 固定 Tool |
| **理由** | 源文档三·6 要求"不执行自由文本命令"；四·规则优先要求"规则能确定时禁止额外调用 LLM"。模型自由选 Tool 同时违反两条，且不可审计、延迟与成本不可控 |
| **否决** | `@n8n/n8n-nodes-langchain.agent` + 11 个 `ai_tool` 子节点 |
| **影响** | LLM 职责被压到"文本 → `{intent, slots, confidence}`"一个函数；出错后果是"路由错了"，不是"直接改了数据库"。**后果可见**：`agent_intent_router` 因此是一个大的确定性 `Switch`，而不是一个 Agent |
| **比赛口径** | LLM 分支**关闭**；`Switch` 的 13 个分支里模型那一路留空 |

## D2 意图判定用规则 `Switch`，兜底一次 `Information Extractor`

| 项 | 内容 |
| --- | --- |
| **状态** | **采纳**（§三 D2） |
| **决定** | 规则层用 `Code` + `Switch`（零成本、可单测）。未命中才进 LLM，且**一次调用**同时抽出 `intent` 与槽位 |
| **理由** | 意图集合有限且互斥（§6.4）；一次出 `{intent, slots}` 省一次往返、省一半 token，且意图与参数由同一上下文决定 |
| **否决** | "Text Classifier 定意图 + 逐分支抽参数"的两次调用方案 |
| **禁止** | 让模型发明 intent 值。枚举外 → `E_UNSUPPORTED`，不得透传。**这条已落成契约**：`intent.schema.json` 的 enum 是封闭的，`tests/fixtures/runtime-validate-llm-output.js` 的手写校验会拒 |
| **影响** | `intent` 枚举在 `intent.schema.json` 与 `response.schema.json` 各出现一次 → **由测试 D-1 锁定一致性** |

## D3 Tool 用 `Execute Sub-workflow`，不用 `toolWorkflow`

| 项 | 内容 |
| --- | --- |
| **状态** | **采纳**（§三 D3） |
| **决定** | Tool 用 `n8n-nodes-base.executeWorkflow` 调用；入口是 `executeWorkflowTrigger` 并**显式声明**输入字段 |
| **理由** | `toolWorkflow` 的参数靠 `$fromAI()` 由模型填；我们走确定性 `Switch`，参数来自已校验的 `slots`，用它等于把确定的值又绕回模型一次 |
| **硬规则** | `userId`、`idempotencyKey`、`requestId`、`confirmToken` **永远从工作流上下文确定性传入，永不经过 `$fromAI()`** |
| **影响** | **这条在契约层的体现**：`request.schema.json` 里 `userId` 被标注为"非权威，仅用于日志比对"；`tool.*.schema.json` 里的 `userId` 由 `agent_gateway` 注入，不由客户端提供（见 `api-spec.md` §二） |

## D4 LLM 输出必须二次校验，解析器必须开 autoFix

| 项 | 内容 |
| --- | --- |
| **状态** | **采纳**（§三 D4），**比赛 MVP 不启用**（链路关闭） |
| **决定** | `outputParserStructured` 用 `schemaType: 'manual'` 写真 JSON Schema；`autoFix: true` + 编码能力强的修复模型；解析成功后**再加**一个 `Code` 节点做第二次独立校验 |
| **理由** | autoFix 解决"JSON 语法坏了"；独立校验解决"JSON 合法但字段值越界"。两道防线拦不同失败模式 |
| **实现注记（F3）** | `ajv` **不在** n8n Code 节点内置白名单里，`require('ajv')` 会失败 → 二次校验只能手写 |
| **影响** | schema 文件（给契约测试看）与手写代码（运行时跑）是**两份**，会漂移 → **由测试 D-4 锁定**：它从 `tests/fixtures/runtime-validate-llm-output.js` 正则提取 `INTENTS` 集合，与 `intent.schema.json` 的 enum 逐项比对 |
| **维护约定** | 主规划 §4.2.5 一改，`runtime-validate-llm-output.js` 必须同步重抄；不同步 D-4 就会红——那正是它的用途 |

## D6 删除确认由 App + 一次性令牌完成，不用 n8n 的 human-review 节点

| 项 | 内容 |
| --- | --- |
| **状态** | **采纳**（§三 D6），**比赛 MVP 无删除路径** |
| **决定** | 二次确认发生在 Android 界面。n8n 侧的强制点是**不透明随机令牌**（32 字节），绑定 `userId + targetId + impactCount + exp`，一次性 |
| **为什么不签名令牌** | 签名防伪造，但要保证**一次性**仍需一次存储查询（记 nonce）。既然总要查一次，不如直接存不透明令牌——**一次 `GET` 拿到全部绑定**，校验后 `DEL`，天然一次性，少一层 HMAC 和一份密钥 |
| **为什么不 n8n human-review 节点** | 需要一个审批渠道和审批人；这里的审批人就是拿手机的用户本人，引入新渠道等于引入新的合规面 |
| **影响** | 源文档 Phase 1 的"危险 Tool 无法绕过确认"变成可写测试：§4.6.3 的 7 个拒绝用例（属 P08） |
| **契约层的落点** | `tool.notes.delete.schema.json` 里 `confirmToken` 的 `minLength: 32`；`confirm-token.schema.json` 里 `userId`/`targetId`/`impactCount`/`exp` **全部必填**——缺任一项令牌就能被借用或挪用 |
| **F5 承重** | E15 证实 Redis 节点 `SET`/`EXPIRE` 非原子，令牌可能没有 TTL → **过期只认 `exp` 字段** |
| **比赛口径** | 删除不进入 MVP；`notes.update` / `notes.delete` 意图统一返回 `E_UNSUPPORTED` |

| **D23** | **每份 Workflow JSON 必须带稳定 `id`；`executeWorkflow` 引用同一个常量** | n8n 的 `import:workflow` 是 `if (!workflow.id) workflow.id = generateNanoId()`——不给 id 就自分配随机串，而引用写的是名字，**永远对不上**。实测症状：子流程调用静默失败、HTTP 200 + 空响应体 | 生成器里 `WF_IDS` 是唯一真源，引用与定义不可能写岔。**Y-7 断言**：每个文件都有 id、且每个 `executeWorkflow` 引用都指向其中之一 |
| **D24** | **`active: false` 是仓库产物的状态；实例里**必须**先 `publish:workflow` 才能互调** | n8n 的 `executeWorkflow` **只调用已发布的工作流**；未发布的子流程会让父流程静默失败 | 这是**部署步骤**，不是仓库产物的问题——所以 JSON 里仍保持 `active:false`（未被部署），发布动作写在 `ops/p11-runtime-runbook.md` 里 |
| **D25** | **真实运行验证是交付的必要条件，不能被"结构绿"替代** | P11 之前三层验证全绿（往返核对 / 规则一致 / `new Function` 行为等价），真实运行**一次抓出 7 个缺陷**，其中两个是"整条链路静默什么都不做" | 复现手册 `ops/p11-runtime-runbook.md` 成为改 Workflow 后的**必跑项**。**这条是本项目最贵的一课** |

### P09（n8 可观测性）追加

| # | 决定 | 理由 | 影响 |
| --- | --- | --- | --- |
| **D26** | **观测链路用「串接」而不是「分叉」；顺序由拓扑确定，不依赖分叉数组的顺序** | **实测逼出来的**。第一版写成 `Shape Response` 同时喂 `Build Log Input` 与 `Respond` 的分叉，指望数组里写在前面的先执行——隔离实例实测**执行顺序是 `Respond` 先、日志后**，与 §4.11「响应返回前调用一次」相反。**把数组顺序倒过来也没有改变结果**：同层分叉的先后在 n8n `executionOrder: 'v1'` 下不可靠。改成 `Shape Response → Build Log Input → Log Request → Respond` 后，顺序由拓扑唯一确定 | 串接把 `Respond` 挪到了日志链路**后面**，于是必须堵两个洞：① 两个新节点**都**要 `continueRegularOutput`（否则一抛异常 `Respond` 就不执行 → HTTP 200 + 空响应体，P11 缺陷 #2/#3 的同一个症状）；② `Respond` 的响应体必须**表达式引用 `Shape Response`**，不能读 `$json`（那时 `$json` 是日志行）。三条都有断言（Y-10 组），并由 **`tools/check-log-order.mjs` 从 n8n 自己的执行数据**里复核 |
| **D27** | **`latency_ms` / `input_length` 取不到就写 `null`，不臆造；补法记账，本轮不做** | `Shape Response` 之后数据流只剩信封那 8 个字段——请求侧的长度与起始时刻**已被有意丢弃**，那是数据边界的要求。`logging-spec.md` 明文：「非数字一律写成 `null`，不臆造」 | 代价是 §9.2 的 p95 延迟指标与"上游连续失败"告警**在本工位无法落地**（`ops/alerts.md` 已逐条标注）。补法（贯穿 router 的 `_meta` 旁路）写在 `observability.md` §4.3，**要动 router 的输出契约，不值得为两个指标去碰刚修过 7 个缺陷的主链路** |
| **D28** | **`report.md` 补上；证据目录改为可传参，绝不复用旧证据路径** | 引导词 P11 的文件所有权点名 `n8n/report.md`，而磁盘上**从来没有过这个文件**——P11 的报告只存在于对话里。"报告在对话里"等于没有交付物。另外：改了 Workflow 就要复跑（D25），而 `p11-runtime-check.mjs` 原先硬写 `ops/p11-evidence/`，一跑就会**覆盖 P11 的原始证据**——那是 7 个缺陷修复前后的对比基线 | `report.md` 按引导词要求四栏分写（已验证 / 推断 / 未验证 / 真机待验）。证据目录由 `UNIMATE_EVIDENCE_DIR` 决定，P09 写 `ops/p09-evidence/`。**改产物路径前先看这条** |
| **D29** | **隔离目录的防漂移断言用「磁盘 ⊆ 清单」单向**，不硬编码条数 | 原先 J 组断言"保留清单恰好 4 条"——**钉死数字的断言每次都会变成"改测试"而不是"发现问题"**。而真正的风险在另一头：守卫是按清单拒绝的，**没登记的目录不在拒绝清单里**（P09 审计时文档 4 条、磁盘 7 个，中间 3 个就是这么漏的） | 改成断言 **Temp 里实际存在的 `unimate-n8n-iso-*` 必须都已登记**（J-1b）。单向：目录被批准删除后仍成立。它当场抓到 P09 自己刚建的两个目录——**这正是它该做的事**；也正因为这条，`open-questions.md` 的 `RESERVED-ISO-DIRS` 块与磁盘**不可能再漂移** |
