## 四 为什么"空"是有意义的（而不是规则太松）

这是本报告最需要解释的一段。**一个永远为空的扫描等于没有扫描**，所以必须说清规则为什么是现在这个形状。

### 4.1 一条**不能**加的规则

看起来最自然、但必须拒收的一条是：

```
（不许）(secret|token|password|key)\s*[:=]\s*["'][^"'\s]{12,}["']     ← 不要加
```

**为什么不能加**：`fixtures/contract-cases/` 里必然有大量这种形状的**合成样例**——
例如 `confirmToken: '<32 字节随机串的样例>'`（`tool.notes.delete.schema.json` 要求
`minLength: 32`，写短了就测不出正常路径）。加上这条规则，扫描结果会**恒定为非空**，
于是每次都要写一份豁免清单。

**而豁免清单正是事故的藏身处**：一旦"这条命中是已知的合成样例"成为习惯，
真正的泄漏就会混在同一份清单里被一起放过。**恒假阳性会训练人忽略扫描结果**——
这比没有扫描更糟。

### 4.2 那怎么保证真实泄漏跑不掉？

真实凭据**几乎总有可识别的格式**（供应商前缀、含密码的 DSN、私钥块、JWT 三段式），
或者出现在**不该出现的位置**。所以本方案在"格式"之外还有三道**位置**检查，
它们可以做到严格而不产生假阳性：

| 检查 | 严格度 | 在哪 |
| --- | --- | --- |
| **凭据格式串**全仓库扫描 | 严格 | 本文件第一节的规则 |
| **Workflow JSON 里不得有凭据值** | 严格（n8n 导出只带引用，不带值） | H 组 |
| **日志节点输出里不得有高熵串** | 严格（日志字段是固定白名单，本该只有 ID/枚举/数字） | D 组 |
| **`credentials/` 只许写名称与用途** | 严格（目录应为空） | H 组 |

**结论**：本报告的"空"是「**没有格式可识别的凭据**」+「**没有出现在不该出现的位置**」，
不是「扫了个空气」。

### 4.3 已知的、刻意留下的

| 项 | 说明 |
| --- | --- |
| `fixtures/contract-cases/` 里的合成令牌样例 | **刻意保留**：它们是契约测试的正例，必须满足 schema 的长度要求。**不是凭据**，且已按本文件 4.1 的理由排除在规则之外 |
| `docs/`、`tests/README.md` 里出现的 `token` / `secret` / `cookie` 等**词** | 是策略文本，不是值。规则按**格式**匹配，不按词匹配 |
| `_comment` / 注释里的说明文字 | 同上 |

## 六 如果命中了一条怎么办

按引导词 P08 的**停止条件**：

> 任何 secret 出现在 diff 或日志时，**立即停止**，报告文件与行号但**不回显 secret**；等待负责人轮换处理。

即：**报告位置，不复制值**。然后停在那里等人处理——**不要**自己判断"这条大概是假的"就继续。
